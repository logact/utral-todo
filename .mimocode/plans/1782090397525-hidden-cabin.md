# CRDT-Compliant Sync Architecture

## Problem

Current sync uses wall-clock `updatedAt` for conflict resolution. Clock skew across devices causes permanent data divergence — the core CRDT principle of **convergence** is violated.

**Concrete example:** Phone clock +5min ahead of laptop. User edits same todo on both offline. Phone's stale edit wins because its `updatedAt` is "newer." Server and laptop adopt phone's version. Laptop's real edit is lost forever.

## Solution: HLC + Per-Record LWW + Tombstones

### Why HLC over alternatives?

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| Wall clock (`Date`) | Simple | Clock skew → divergence | ❌ Current bug |
| Vector clocks | Perfect causal ordering | O(n) size, no wall clock time | ❌ Can't query "since last sync" |
| Lamport timestamp | O(1), causal ordering | No wall clock time | ❌ Same problem |
| **HLC** | O(1), causal + wall clock, deterministic tie-breaker | Slightly more complex than wall clock | ✅ |

### Why per-record LWW (not per-field)?

- Todo app rarely has concurrent edits to **different fields** on the **same record**
- Per-field CRDTs (Automerge/Yjs) add heavy dependency for negligible benefit
- Per-record LWW with HLC is correct, simple, and sufficient

### Why tombstones?

- Hard deletes can't be reconciled with creates during partition
- Tombstone = soft delete (`deletedAt` timestamp) that propagates via sync
- GC after 30 days to prevent unbounded growth

## Data Model Changes

### HLCTimestamp

```typescript
interface HLCTimestamp {
  wall: number;    // ms since epoch
  counter: number; // logical counter (increments on same ms)
  node: string;    // deviceId (tie-breaker)
}
```

### Entity changes

Every entity gets:
```diff
- updatedAt: Date
+ updatedAt: HLCTimestamp
- createdAt: Date
+ createdAt: HLCTimestamp
+ deletedAt?: HLCTimestamp
```

### Merge rules (identical on server + all clients)

```
Given local L and remote R (same id):
1. L is null → adopt R
2. R is null → keep L
3. R.deletedAt > max(L.updatedAt fields) → apply tombstone
4. L.deletedAt > max(R.updatedAt fields) → keep deleted
5. R.updatedAt > L.updatedAt → adopt R
6. R.updatedAt < L.updatedAt → keep L
7. Equal → use node (deviceId) as tie-breaker
```

These rules are **commutative, associative, idempotent** → convergence guaranteed.

## Verification

1. **Clock skew:** Set device A +5min ahead, edit same todo on both offline, reconnect → all converge to HLC-determined winner
2. **Concurrent offline edits:** Both devices edit same record offline → server and all clients end up with same version
3. **Delete vs edit:** Delete on A, edit on B → if B's edit is newer by HLC, record is restored
4. **Offline reconnection:** Device offline 24h, make edits, reconnect → all changes merge correctly
5. **Tombstone propagation:** Delete on A → appears deleted on B → cleaned up after 30 days
